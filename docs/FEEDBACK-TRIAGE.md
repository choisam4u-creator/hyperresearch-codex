# 제보를 재현 가능한 수정으로 연결하기

새 리서치를 반복 실행시키기보다 사용자가 이미 얻은 결과를 자발적으로 제공하는 방식으로 시작한다. 첫 목표는 소수 사용자에게서 설치와 사용 장애를 찾는 것이며 통계적 품질 입증이 아니다. 제출 방법은 [FEEDBACK.md](FEEDBACK.md)를 따른다.

## 접수와 분류

1. 성공/실패 모두 받는다. 설치 실패, 실행 중단, 결과 활용도, 출처와 연결된 품질 문제를 구분한다.
2. 공개된 최소 정보만 확인한다. 원문·개인정보가 포함되면 추가 복제를 피하고 작성자에게 삭제/수정 방법을 안내한다. API 키가 노출되었다면 작성자가 폐기해야 하며 로그에 복사하지 않는다.
3. 같은 버전·설정·증상은 기존 이슈와 연결한다. 중복 제보는 사용자 경험 수로는 보존하되 독립 오류 종류나 독립 실험으로 중복 집계하지 않는다.
4. `hpr feedback`의 품질 상태는 자동 검사 결과다. 사용자의 만족도, 원문 기반 사실 판정과 혼합하지 않는다. 상태가 없으면 미확정이다.

## 재현과 수정

- 설치·런타임 문제: 가짜 CLI/임시 파일/mock backend로 최소 재현한다.
- 품질 문제: 사용자가 공개한 문제 문장과 접근 가능한 공개 출처의 해당 근거를 대조한다. 출처를 확보하지 못하면 사실 오류 확정 대신 확인 불가로 남긴다.
- 원문을 저장소 fixture로 재배포할 권한을 확인할 수 없으면 동일 실패 구조의 합성 문장으로 축소한다. 실제 제출 원문과 합성 재현을 구분한다.
- 수정 전 실패·수정 후 통과와 정상 대조 사례를 함께 둔다. 검수자는 적용 코드와 결과를 확인하고 이슈가 남으면 수정 후 다시 검수한다.
- 결과 기록에는 버전/커밋, 재현 여부, 수정 범위, 검사 명령, 남은 한계를 포함한다. 댓글·외부 대응은 운영자의 승인 범위를 따른다.

## 집계 정의

| 지표 | 분모와 범위 |
|---|---|
| 설치 성공 비율 | 설치 결과가 명시된 유효 제보만. 저장소 방문자 전체의 성공률이 아님 |
| 실제 실행 완료 비율 | 실제 실행 여부와 완료 상태가 확인된 제보만. demo/mock는 별도 |
| 사용자가 그대로 활용한 비율 | 활용도에 답한 제보만. 정확도 측정이 아님 |
| 재현된 품질 문제 | 공개 근거와 문제 문장을 대조하여 확인한 독립 문제 종류 |
| 토큰 비교 | 모델·언어·입력·설정이 비교 가능한 쌍만. 캐시 입력은 입력의 부분집합이며 다시 합산하지 않음 |

결측/미측정/미응답을 0이나 성공으로 바꾸지 않는다. 유효 표본 수와 제외 사유를 함께 기록한다. 알려진 사례의 수정과 새 독립 평가를 구분한다. 자발적 제보에는 선택 편향이 있으므로 전체 사용자 또는 일반 품질·절감률로 확대하지 않는다. 별, 다운로드, 조회 수를 실제 사용·품질 데이터로 대체하지 않는다.

## 지금 준비된 것과 실제 데이터

이 문서는 수집·재현 절차다. 외부 사용자 테스트 결과나 모집 완료를 뜻하지 않는다. 자동 업로드/백그라운드 수집/새 모델 호출은 없다. 실제 제보가 들어온 후 위 기준으로 다음 수정 후보를 선정한다.
