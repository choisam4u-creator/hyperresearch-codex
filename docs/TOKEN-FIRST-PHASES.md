# Phase 8–13: 토큰 우선 개선 (2026-09-14)

목표는 같은 질문과 출력 요구를 만족하는 보고서 한 건에 필요한 전체 토큰을 줄이는 것이다. 실패·재시도·품질 미달 실행도 비용에 포함한다. 아래는 로컬 구현 상태이며 원본 hyperresearch 대비 우위나 실제 절감률을 입증한 결과가 아니다. Windows 실제 모델 실행과 외부 설치 피드백은 이번 범위에서 제외했다.

## 토큰 보호 사용법

```bash
hpr run "조사 질문" --preset economy --budget 500000 --max-calls 24 --plan-json
hpr run "조사 질문" --preset economy --budget 500000 --max-calls 24
hpr resume RUN_ID --budget 700000 --max-calls 28
```

첫 명령은 모델·검색 호출 없이 계획 JSON만 출력한다. 두 번째는 실제 리서치를 실행한다. 예시 예산은 성능 보장이 아니다. `economy`는 실험 후보이며 기본값은 계속 `standard`다. 사용자가 지정한 `models`, `budget`, `verification`, `routing` 설정이 프리셋보다 우선한다.

`economy`는 재시도 0회, 총 시도 24회, 미측정 사용량 발생 시 다음 호출 중단, 입력 예약 검사를 사용한다. 역할은 Luna(검색/다듬기), Terra(분석/비평/수정), Sol(심층 조사/작성/종합), Astra(인용 검사)로 나눈다. 높은 심각도의 지적이 있으면 기존 수정 호출의 역할을 Astra로 최대 한 번 바꾼다. 승격 자체가 호출을 추가하지 않는다. 모델 접근 가능 여부와 실제 비용 효율은 별도 확인해야 한다.

입력 예약은 UTF-8 크기와 관측된 역할별 입력량을 이용한 보수적 추정이다. 모델의 내부 도구 사용과 출력 토큰까지 강제 제한하는 결제 상한은 아니다. 이미 실행 중인 호출은 추정보다 많이 사용할 수 있다. `--max-calls`는 실패·재시도를 포함하며 재개에도 유지된다. 미측정 호출은 0토큰으로 간주하지 않는다. 캐시 토큰은 입력에 포함된 부분이므로 합계에 두 번 더하지 않는다.

재개는 첫 실행의 설정을 유지하며 예산·호출 상한은 resume 옵션으로 변경한다. 유효 설정과 호출별 구성 해시를 기록한다. 코드나 프롬프트가 바뀐 상태에서 추가 모델 호출은 막으며, 기존 버전 복원 또는 새 실행 ID가 필요하다. 예산 등 조건이 도중에 바뀐 실행은 통제 비교에 사용할 수 없다.

## 선택 기능과 산출물

`research/config.json`의 `verification.recheck_changed: true`는 Full 다듬기 뒤 변경되거나 아직 검사하지 않은 인용 문장을 한 번 추가 검사한다. `cite_sample`까지만 선택하고 추가 호출 재시도는 하지 않는다. 같은 문장이라도 출처·검증 프롬프트·모델 설정이 바뀌면 이전 판정을 재사용하지 않는다. 나머지 미검증 범위를 표시한다. 기본값은 false다.

`verification.require_traceability: true`는 원장의 연결이 부족한 후보가 있으면 검토 대상으로 만든다. 원장은 마크다운 구조상의 후보이며 완전한 의미 주장 추출기가 아니므로 기본값은 false다. 지원 관계나 날짜를 알 수 없으면 `unchecked` 또는 `unknown`을 유지한다. 부분 수정 성공만으로 높은 심각도 지적을 해결 처리하지 않는다.

`gap_fetch.enabled`의 선택 보충은 기본 OFF다. 기존 상한과 `--no-search`를 지키며 저장된 출처를 우선 사용한다. [기존 개발 단계](DEVELOPMENT-PHASES.md)의 보충 설정을 함께 참고한다.

새로 끝난 실행은 `evidence_ledger.json`, `usage_summary.json`, `review.md`를 남긴다. `review.md`는 결과 일부와 경고를 옮긴 짧은 검토 페이지로 별도 모델 호출이 없다. 실행의 `quality.status=passed`는 자동 검사 범위 통과이며 사실 정확도 인증이 아니다.

## 다음 순서와 완료 기준

1. 로컬 회귀와 격리 wheel mock 실행으로 구현을 검증한다.
2. 실제 실험 질문·횟수·전체 토큰 예산을 정한 뒤 개발 입력으로 기준선과 후보를 비교한다. 모델 선택만 바꾸는 비교와 코드 변경 비교를 분리하고 같은 출력 요구를 유지한다.
3. 개발 결과로 설정을 고정한 뒤 보류 8개를 평가한다. 보류 정답을 프롬프트나 튜닝 입력에 넣지 않는다.
4. 같은 품질에서 토큰 절감이 확인된 설정만 기본값 변경 후보로 삼는다. 의미 주장 분해·반대 근거 판정·출력 유형 확장을 이어 간다.

초기 목표인 근거 지지 95%, 질문 충족 90%, 평가셋 치명 오류 0, 오류 탐지 95%/오경고 5% 이하, 자체 기준선 대비 토큰 30%·시간 20% 절감은 모두 **미측정 목표**다. 합성 자료 개수나 mock 테스트 통과를 이 목표 달성으로 계산하지 않는다. 원본 프로젝트를 능가했다는 판단에는 원본과의 동일 입력·품질·출력 조건 실측도 필요하다.
